# CLAUDE.md — bluesky

This file provides guidance to AI coding agents (such as Claude Code) when working with code in this repository.

`bluesky` is an experiment-orchestration library for Python: you describe a measurement as a *plan* — a generator that yields `Msg` objects — and the `RunEngine` executes it against hardware, emitting documents (start/descriptor/event/stop) to subscribed callbacks. It pairs with the `ophyd` device-abstraction library (a separate, public sister project this code references throughout).

## This is a maintained fork

This repository is a fork of [`bluesky/bluesky`](https://github.com/bluesky/bluesky). Treat upstream as the source of truth for design and style:

- **Keep every change minimal and surgical.** Prefer the smallest diff that solves the problem; avoid refactors, reformatting, or churn that increases divergence from upstream.
- **Match the existing code style** rather than imposing new conventions — changes should read as if they could be contributed back to upstream.
- Keep the public API (`bluesky/__init__.py`, `bluesky/plans.py`, `bluesky/plan_stubs.py`, `bluesky/protocols.py`) stable; adding to it is a deliberate decision, not a side effect.
- Do **not** touch `src/bluesky/_vendor/` — it is generated by the vendoring tool, not hand-edited.

## Public fork — confidentiality boundary

This is an **open, world-visible** fork. Attribution is fine here: it is openly owned by its organization and committing under the usual identity is expected — there is no need to anonymize authorship. What must **never** appear in this repository (code, comments, docstrings, tests, examples, commit messages, or branch names) is **confidential information** from the private downstream projects that depend on it:

- names of private/internal packages, modules, or repositories;
- proprietary algorithms or business logic copied out of private code;
- internal infrastructure, hostnames, deployment details, credentials, secrets, or lab data;
- specific instrument/hardware identifiers and vendor-proprietary specifics.

Every change must read as a generic, upstream-appropriate contribution to the public library — as if opening a PR against `bluesky/bluesky`, with no trace of any private consumer. A **pre-push contamination guard** (installed per-clone, never committed) scans pushes for these identifiers and aborts if any appear; it is a backstop, not a license to be careless. The reverse direction — private code depending on this library — is fine; that's just using a public package.

## Type checking

Upstream type-checks with **mypy** (`mypy src`, configured under `[tool.mypy]`; also exposed as the tox `type-checking` env). The package ships `py.typed`, so its annotations are consumed by downstream code.

The **active reason for working in this fork** is improving those annotations: at least one downstream consumer type-checks with **pyright in strict mode** (others run pyright in standard mode or not at all), so gaps or imprecise types here surface as pyright errors there. When tightening annotations:

- Keep mypy passing (`mypy src`) — don't regress the upstream checker while satisfying pyright.
- Keep additions **honest**: prefer specific types, `Protocol`s, `TypedDict`/`NamedTuple`, generics, and narrowing (`assert`, `isinstance`) over `# type: ignore`, `cast()`, or `: Any` used merely to silence a checker. Where the runtime is genuinely dynamic or an invariant is true-but-unprovable, a narrow `cast`/`Any` is acceptable — leave a one-line comment saying why.
- Stay minimal and upstream-compatible so the change could be contributed back (annotation-only diffs are ideal).

## Branch workflow

- AI-agent changes happen on dedicated `claude/*` branches, never directly on `prod` or `main`.
- Day-to-day work: branch `claude/feature/<name>` off `claude/main`, PR back into `claude/main`.
- `prod` is the integration branch that downstream pins to. Promoting work to production is a **separate `claude/main` → `prod` PR**, reviewed and merged **manually** by the maintainer — an agent may open such a PR on request but never merges it.
- Keep `prod` clean and easy to compare against upstream `bluesky/bluesky`.

## Architecture

The package lives under `src/bluesky/`. The pieces that do the real work:

### `run_engine.py` — the executor
- `RunEngine` and `RunEngineResult` (the run outcome) are defined here. `RunEngine` consumes a plan (a generator of `Msg`), runs it to completion against hardware, manages the asyncio loop, run state, interruptions (pause/resume/abort/halt), and document emission.
- Module-level event-loop helpers also live here (`set_bluesky_event_loop`, `autoawait_in_bluesky_event_loop`) — used by consumers that drive the engine from their own loop.
- Note: `RunEngineInterrupted` (signals a paused/stopped run) is **not** defined here — it lives in `utils/__init__.py` and is re-exported from the top-level `bluesky` package (consumers do `from bluesky import RunEngineInterrupted`).

### `Msg` and the plan vocabulary
- `Msg` (a `namedtuple` in `utils/__init__.py`) is the instruction unit — `Msg(command, obj, *args, **kwargs)` (e.g. `set`, `read`, `trigger`, `open_run`, `save`). `MsgGenerator` (also in `utils`) is the type alias for a plan: a generator yielding `Msg`. `utils` is also where several top-level `bluesky` exports originate — `RunEngineInterrupted`, `FailedStatus`, `IllegalMessageSequence`.
- `plan_stubs.py` — the small primitive plans (`mv`, `abs_set`, `trigger_and_read`, `open_run`, `save`, …) that compose into larger ones.
- `plans.py` — the full pre-built experiment plans (`count`, `scan`, `grid_scan`, `list_scan`, …).
- `plan_patterns.py` — geometry/trajectory helpers used by the scans (e.g. spiral, grid outer-product cycles).
- `preprocessors.py` — plan *mutators* (e.g. `baseline_wrapper`, `monitor_during_wrapper`, `relative_set_wrapper`) that wrap a plan to inject behavior.

### `protocols.py` — duck-typed hardware interfaces
- Runtime-checkable `Protocol`s (`Readable`, `Movable`, `Triggerable`, `Flyable`, `Configurable`, …) the `RunEngine` uses to talk to devices without importing any concrete driver. This is the primary surface where annotation precision matters to typed consumers.

### `callbacks/` — document consumers
- Subscriptions that receive the emitted documents: `LiveTable`, `LivePlot`, the best-effort callback, `CallbackBase`, etc.

### Supporting modules
- `bundlers.py` (document assembly during a run), `suspenders.py` (auto-pause conditions), `simulators.py` (`summarize_plan`, `check_limits` — inspect a plan without hardware), `log.py`, `magics.py` (IPython integration), `tracing.py`, `consolidators.py`.

## Conventions

- Don't swallow exceptions silently; if a handler must catch, leave a comment justifying why dropping the error is safe.
- When changing run-engine or plan semantics, add or update a test under `src/bluesky/tests/` and keep affected docstring examples runnable — they double as documentation and are executed by the doctest config.
